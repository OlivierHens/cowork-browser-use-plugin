# Interaction Patterns

How to identify elements, pace actions, and handle common page behaviors so the browser session reads as a person, not a bot.

## Identifying targets — priority order

Use the first one that's unambiguous:

1. **Visible text.** "the *Sign in* button", "the link reading *Skip to content*". Most reliable because it matches what a human sees.
2. **Form label.** "the field labeled *Email address*". Use whenever there's a visible label, even if the input has no `name` attribute.
3. **ARIA role + accessible name.** `role="button" name="Search"`. Use when text is missing (icon-only buttons).
4. **Position relative to a landmark.** "the first link inside the *Top stories* section". Use when the page has duplicate text but a clear structure.
5. **nth-of-type / CSS selector.** Last resort. If you're reaching for this, double-check that `read_page()` doesn't give you a stable name first.

**Never** identify by `id` alone unless `read_page()` shows that id in the structured output — autogenerated SPA ids change between loads.

## Pacing

- After `navigate()`: wait briefly (1–2 s) before the first screenshot on heavy pages. SPAs render twice.
- After `click()`: usually no wait. Only insert one if the next screenshot looks like the click hasn't landed yet.
- After `type()`: don't immediately submit. Take a screenshot first to confirm the value showed up — autocomplete, masking, and password-strength widgets sometimes consume keystrokes.
- Don't batch multiple `type()` calls without a screenshot in between on long forms. Forms with conditional fields (a country dropdown unlocking a state dropdown) will surprise you.

## Scrolling

- **Always scroll the target into view before clicking it.** Clicking offscreen elements is the #1 cause of "the click didn't seem to do anything".
- For "infinite scroll" feeds: scroll a screen-and-a-half at a time, screenshot, check if new content rendered. Stop after 5 scrolls with no new content.
- For pages with sticky headers, your target may be visually covered after a scroll. Re-screenshot before clicking.

## Lazy-loaded content

- Images and below-the-fold widgets often render in stages. If a screenshot shows a placeholder/spinner where content should be, wait 2 seconds and re-screenshot once before declaring failure.
- For lists that load on scroll (Twitter/X-style feeds), a short scroll often triggers the load even when there's content visible.

## Autocomplete and dropdowns

- Native `<select>` elements: `click()` to open, then `click()` the option by visible text.
- Custom comboboxes (React-Select, etc.): type a few characters, *wait*, then click the matching option. Don't press Enter unless you've seen the option highlight in a screenshot.
- Date pickers: prefer typing into the input if the field accepts it. Calendar-only pickers need stepwise clicking through months — slower, but more reliable than guessing keyboard shortcuts.

## Forms

- Read the whole form first via `read_page()`. Note which fields are required.
- Fill from top to bottom in visible order.
- For multi-page forms: confirm the page advanced by screenshotting after Next/Continue. Don't assume.
- Before pressing the final Submit / Pay / Confirm:
  1. Screenshot the summary.
  2. State out loud what's being submitted and to which domain.
  3. Pause for the user.

## Multiple tabs / popups

If a click opens a new tab or window:

- Note it in your narration ("a new tab opened for the OAuth flow").
- Switch focus only if the connector supports it; otherwise treat the popup as the user's to handle and pause.

## Iframes

If you can see content in a screenshot but `read_page()` doesn't include it, it's probably in an iframe. Many connectors will need an explicit `switch_to_frame` (or equivalent). If your server doesn't expose that, surface the limitation to the user rather than guessing.
